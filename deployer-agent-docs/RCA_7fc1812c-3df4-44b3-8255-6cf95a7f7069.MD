## TL;DR root cause
Every unapproved note-bearing packet trips the blocker because **`signer` resolves to `None`** in `_approval_blockers`.
- Notes store provider/signer as **free-text names only**. The fields `attending_provider_id`, `signed_by_id`, `author_id` are **ABSENT on every note** (so `assigned`/`signer` fall through to `resolve_provider_id(name)`).
- `attending_provider` = "Saday Cabrera" on **all** notes → `resolve_provider_id` loosely matches the psychologist **Saday Cabrera Rodriguez** (`c7c1f453…`, role=psychologist, a CLINICAL_ROLE) → **assigned is NOT None**.
- `signed_by` is **"Clinic Admin"** or **"Printiss Temple"** on every signed note. Both are **role=admin**, which is **excluded from CLINICAL_ROLES** (doctor/nurse/psychologist). `resolve_provider_id` therefore finds no candidate → **signer = None** → blocker fires.
- Secondary: even if admins were resolvable, `assigned` (Saday, psychologist) ≠ `signer` (an admin) → the `assigned != signer` branch would still fire. The signatures are valid images but are attributed to an admin, not to the attending provider.

## Suggested fix (no change applied — read-only investigation)
This is a logic/data-model issue in the app source (backend/routers/claims.py `_approval_blockers`, backend/core/providers.py `resolve_provider_id`):
1. Signer never resolves because the real signers are admin-role users (Clinic Admin, Printiss Temple), and `resolve_provider_id` only searches CLINICAL_ROLES. Decide intended behavior and fix in code: e.g. resolve the signer against ALL active users (or include admins), and/or persist `signed_by_id`/`attending_provider_id` on notes at sign time instead of relying on fuzzy name matching.
2. Even once the signer resolves, the attending provider is "Saday Cabrera" (psychologist) while signatures belong to admins — so a strict `assigned == signer` rule will still legitimately flag these. The clinic/product owner must decide whether an admin/delegate signature should satisfy the "signed by assigned provider" requirement (e.g. co-sign model, or require the attending provider to sign), because the current DATA genuinely has admins signing on behalf of the attending provider.
3. Separately, repair the dangling reference: packet 9ca702b5 points at a non-existent note d294ee0a.
