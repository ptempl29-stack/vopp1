## ROOT CAUSE — the signing rule DOES block the provider (confirmed)

The signing authorization in `backend/routers/notes.py` (`_is_note_provider`, lines 48–56) authorizes a signer by matching the note to a clinical account id, with this precedence:
1. `user["id"] in (note.author_id, note.attending_provider_id)` — short-circuit by stored id.
2. else resolve `note.attending_provider` (free text) to exactly ONE clinical account via `_resolve_provider_id`.
3. else resolve `note.author` (free text) the same way.

`_resolve_provider_id` (lines 38–45) normalizes with `_norm_name` (lowercase, strip a `dr/dra/lic/...` title prefix, collapse spaces) and requires an EXACT normalized-string equality to a clinical user's name, returning that id only if exactly one matches.

Applying this to the data:
- Path 1 cannot fire: `author_id` and `attending_provider_id` are present on **0** of 224 notes.
- Path 2: note `attending_provider` = "Saday Cabrera" → normalized `"saday cabrera"`. The account normalizes to `"saday cabrera rodriguez"`. `"saday cabrera" != "saday cabrera rodriguez"` → 0 matches → returns None → no match.
- Path 3: note `author` = "Saday Cabrera" (197 notes) → same `"saday cabrera"` → same mismatch → None.

Therefore `_is_note_provider` returns False for the psychologist account on these notes, so update_note (notes.py:130–131) raises 403 `"Only the note's attending or authoring provider may sign this note"`. This matches the one observed 403 on `PUT /api/notes/4b292eac...`.

Underlying cause: a data/name-shape mismatch — the notes store the legacy free-text provider as "Saday Cabrera" while the account is "Saday Cabrera Rodriguez", and no note carries the `attending_provider_id` / `author_id` that would let the id-based path (step 1) bypass the fragile exact-name match. The newly deployed rule tightened signing to exact-name/id resolution, which these legacy rows fail.

## SECONDARY, UNRELATED BUG — attachment download 500
`download_attachment` (messages.py:89) builds a `Content-Disposition: attachment; filename="..."` header from the stored filename. The code strips quotes/newlines but not characters outside latin-1. A filename containing U+202F (narrow no-break space) raises `UnicodeEncodeError` when Starlette latin-1-encodes the header → 500. Any attachment whose filename contains a non-latin-1 character will 500 on download.
