# RCA — veteran-care-portal (veteransofpuertoplata.com): intermittent "network error" then self-recovery

## Verdict
**OOM / resource-limit driven.** The production backend pod is being **OOMKilled (exit code 137)** because it exceeds the tier_0 memory limit (512Mi) under active use. When a replica's backend process is killed, its co-located nginx has no upstream and returns connection-refused/503 to every request (save note, login, everything) for the ~60–90s it takes uvicorn to restart. Once it's back up, the app works again. This exactly matches "network error on save → kicked to login → login also fails → works again after a few minutes."

This is a **runtime resource problem, not an auth bug and not a code regression from the last deploy.**

## Evidence (from production runtime data)

### 1. Pod restart / kill history — CONFIRMED OOM
- Active run `332aba5c-e5fd-4496-86f9-136de5b7ff7e`, cluster target-8.
- `last_termination`: **reason=OOMKilled, exit_code=137**, finished_at **2026-09-20T13:11:53Z**, restart_count=1.
- Startup/liveness/readiness probes to `http://<pod>:8080/health` returned **503** and then **connection refused** during the restart window (13:11:50 → 13:12:59).
- A second, earlier crash-recovery cycle is visible in logs on **2026-09-19 ~20:23:58–20:24:58** (repeated nginx `connect() failed (111: Connection refused)` to `127.0.0.1:8001/health`), i.e. this has happened more than once.

### 2. Backend logs around the failure windows
- Right before the kill: `upstream timed out (110) while reading response header from upstream ... /health` (backend unresponsive under memory pressure), then a burst of `connect() failed (111: Connection refused)` (backend process gone), then `Application startup complete` / `Uvicorn running on 0.0.0.0:8001` (restart → recovery).
- No application traceback/MemoryError is emitted — expected for an OS-level OOM kill (the kernel kills the process; Python cannot log its own death). The K8s OOMKilled signal is the authoritative cause.

### 3. Resource limits / tier — under-provisioned
- Current tier: **tier_0 "Starter"** — CPU request 50m / limit 250m, **memory request 200Mi / limit 512Mi**, replicas=2, HPA/VPA disabled.
- 512Mi is very tight for a FastAPI app that also builds/merges PDFs with PyMuPDF (fitz) + font subsetting.

### 4. PDF / claim-packet correlation — SUPPORTED
- Production logs show the PDF code path is active: `POST /api/invoices/{id}/to-folder` immediately followed by `INFO:fontTools.subset:post subsetted` / `post pruned` (font subsetting during PDF assembly). PyMuPDF page rendering + font embedding + holding a full packet in memory can spike RSS well past 512Mi on a large packet, tripping the OOM killer. In-flight requests at the moment of the kill get no HTTP response (client sees "network error"); they are not logged as 500s because the worker dies mid-request.

### 5. MongoDB / DB health
- No Mongo connection errors, pool-exhaustion, or Atlas timeouts in the logs. `/api/*` reads/writes return 200 when the backend is up. DB connectivity is **not** the cause — the failures are the OOM-driven restart gaps, not DB drops.

### 6. Login-failure coincidence — CONFIRMED it's downtime, not auth
- `POST /api/auth/login` returns 200 when the backend is up. The login "network errors" occur only during the connection-refused/503 restart windows — i.e. the backend is simply unavailable, not rejecting credentials. (401s seen in logs are ordinary unauthenticated `/api/auth/me` / `/api/hidden-options` probes, not failed password attempts.)

### 7. Deploy correlation — NOT caused by the recent deploy
- Last successful deploy: run `332aba5c...` completed **2026-08-19T15:23:39Z**. The observed OOM kills are **2026-09-19 / 2026-09-20** — about a month later. So onset does **not** line up with the deploy; this points to growing usage/data/packet sizes hitting the fixed 512Mi ceiling over time, rather than a code regression shipped in the last release.

## Why it's intermittent and self-healing
Two replicas, and each pod's nginx proxies to its **own** local backend (`proxy_pass http://127.0.0.1:8001`). When one replica OOMs, only requests routed to that pod fail; the other pod may still serve — and the failing pod recovers on restart in a minute or two. Hence "fails, then fine again," dependent on which replica a request lands on and whether a memory spike is in progress.

## Recommended fix (in priority order)
1. **Raise the deployment tier** (immediate mitigation). Move off tier_0 (512Mi) to tier_1 "Launch" or higher via Deployment Panel → Resources. This is the fastest way to stop the OOM kills. Given PDF/packet memory spikes, tier_2 "Grow" may be warranted if tier_1 still OOMs on large packets.
2. **Reduce peak memory in the PDF/claim-packet path** (durable fix, code-side — owned by the app/source agent):
   - Stream/write PDFs to a temp file and merge incrementally instead of holding the whole packet + all page pixmaps in memory.
   - Explicitly close PyMuPDF documents (`doc.close()`) and free pixmaps; avoid rendering at unnecessarily high DPI when stamping cover sheets.
   - Cap/guard maximum packet size or process very large packets as a background job.
   - Subset fonts once/cache rather than per-request if possible.
3. **Operational**: consider enabling autoscaling/more replicas at the higher tier so a single heavy PDF request can't take down the only serving replica; keep an eye on restart_count after the change.

## Bottom line
Not a DB issue, not an auth bug, not a regression from the last deploy. It is **memory exhaustion (OOMKilled/137) on the tier_0 512Mi ceiling, aggravated by memory-heavy PDF/claim-packet generation (PyMuPDF + font subsetting)**. Raise the tier now; optimize the PDF path to make it durable.
